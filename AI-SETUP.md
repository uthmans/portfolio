# Survey Insights Studio: feedback analysis

The public GitHub Pages site can run the hand-written fictional example without credentials. It never presents that example as an AI result and never uses it to analyse imported feedback. Ratings and written feedback share one CSV: add the optional `feedback` column to the five required rating columns. Both sections use the same filters. Importing stays in the tab; only nonblank selected comments are sent after consent and an explicit AI request. At most 100 comments may be analysed per request; larger selections require filters rather than silent truncation. Changing data or filters clears stale results and consent. Theme dropdowns show the finding and original responses together.

## Cloudflare setup for this portfolio

The repository now includes a Cloudflare Worker in `worker/index.mjs` and `wrangler.jsonc`. Your portfolio stays at `https://uthmans.github.io/portfolio/`; Cloudflare hosts only the AI helper at `https://portfolio.uthmansalama.workers.dev`.

1. In Cloudflare, open **Workers & Pages → portfolio → Settings → Variables and Secrets**. Add `SURVEY_AI_KEY` as a **Secret** containing your OpenAI API key. Keep it out of GitHub, build variables, Vite variables and chat. If it is already saved, do not duplicate it.
2. The Cloudflare Git integration should track `main`, with root directory `/`, no build command, and deploy command `npx wrangler deploy`. The new Wrangler file selects the backend entry point and creates the SQLite-backed Durable Object for shared usage limits. It preserves the existing secret. A push triggers a new build if automatic builds are enabled; otherwise use Cloudflare **Retry build** for the newest commit.
3. After deployment, visit `https://portfolio.uthmansalama.workers.dev/api/health`. It should show `"ready":true`. This checks presence of the secret and quota binding; it does not test OpenAI billing, key permissions or model access. The root URL shows this service status too, rather than a second website.
4. GitHub Actions builds the portfolio with the public endpoint URL. Once both deployments succeed, open the survey on GitHub Pages, find written feedback, check consent and click **Analyse feedback**. Try the fictional sample first; then check findings against source responses. This makes a billable OpenAI request.
5. If `ready` is false, check the secret's name and that the newest Worker deployment succeeded. A 502 after a request may indicate missing OpenAI credits, a key without API permission, model access, a timeout or invalid model output. Keys and provider diagnostics are never returned to the browser. A 429 means the demo quota was reached; failed provider requests also consume a reservation.

Health diagnostics include `version: "health-check-2"` and two safe booleans under `checks`: `apiKeyConfigured` and `quotaBindingConfigured`. If the dashboard shows both settings but either boolean is false, the active deployed version does not receive that setting. Ensure the latest version with those settings is deployed to Production; an edited or saved version is not proof it is serving traffic. Do not recreate a correct binding or rotate a valid key merely to troubleshoot this. If the version marker is missing, the URL is serving older code. These checks never return the key, its length or its prefix.

The public Worker allows 3 requests per IP address per UTC hour and 20 total per UTC day. Quotas persist across Worker restarts/deployments, are reserved atomically and count failed AI attempts. Only a SHA-256 hash of the client IP and counters are stored in quota state; no survey text is stored by our application. People sharing an IP share the hourly limit. These are request limits, not a monetary guarantee: configure provider account spending controls as well. The public endpoint has no user login; CORS is not authentication and callers outside a browser can spoof Origin. Global quotas bound public-demo usage, but an attacker could exhaust that allowance. Add Turnstile or authentication before raising limits for broader use. Worker request logging is disabled in the repository configuration to avoid recording application data.

Developer checks: `npm test`, `npm run worker:check` (Wrangler bundle dry run), and `npm run worker:dev` for the local Cloudflare runtime. On restricted workspaces, set `XDG_CONFIG_HOME` to a writable directory, for example `/tmp/portfolio-cf-config`, and `WRANGLER_SEND_METRICS=false`. No Cloudflare token or OpenAI key is needed for the bundle check or mocked tests. Never run a remote deployment unless authorised; this project uses the user's existing Git-triggered Cloudflare deployment.

## Alternative local Node backend

1. Obtain an OpenAI API project key with a small spending budget. Set `SURVEY_AI_KEY` securely in the backend process environment. Do not paste it in chat, commit it, or use a `VITE_` variable for it. The backend uses the OpenAI Chat Completions endpoint; `SURVEY_AI_MODEL` defaults to `gpt-4.1-mini` and can be set to a compatible model available to your account.
2. Run `node server/feedback.mjs` from this checkout. The server binds only to `127.0.0.1:8787` by default. `SURVEY_AI_PORT` overrides the port. No extra npm dependencies are required.
3. Start Vite with the non-secret variable `VITE_FEEDBACK_API_URL=http://127.0.0.1:8787/api/feedback` using `npm run dev -- --port 5173 --strictPort`. Access development using `127.0.0.1`, matching the default allowed origin. If using another origin, set `SURVEY_ALLOWED_ORIGIN` to that exact scheme/host/port in the backend. Vite needs restarting after changing its environment.
4. Import anonymised feedback or use the fictional sample, check the consent box and request AI analysis. Check source responses, contradictory opinions and unsupported claims before acting. Model output is validated structurally and against known IDs; semantic accuracy is not guaranteed.

## Other hosting options

GitHub Pages cannot run this Node backend. Keep the frontend on Pages and host the backend separately. Choose hosting with a managed HTTPS gateway, real authentication or bot protection, persistent per-client rate limits and spending controls. The supplied server is a local integration reference, not an unrestricted public endpoint: CORS is not authentication, and its global 20-requests/hour limit is in memory, resets on restart and does not coordinate replicas. Put the loopback service behind the gateway, or adapt it to your chosen platform's serverless handler. Never put a shared gateway secret in public frontend code.

Set the backend's allowed origin to `https://uthmans.github.io` (origins do not include `/portfolio/`). Set the frontend build variable `VITE_FEEDBACK_API_URL` to the public HTTPS endpoint, then rebuild and redeploy. Without this variable the site clearly reports live AI as disconnected. The existing GitHub Pages workflow now supplies the Cloudflare endpoint; it contains no key.

Review your provider's data retention and processing terms before collecting third-party feedback. Remove identifying and sensitive text; the report download contains source feedback. The supplied service does not log or persist request text and sends it only to `api.openai.com`. Configure gateway/hosting logs accordingly. The backend applies size/count/text bounds, one concurrent request, timeouts, a model output-token limit, and source-ID validation. Feedback is passed as untrusted user data with instructions to resist embedded commands; this reduces but does not eliminate prompt-injection risk. The UI renders results as text, never model HTML.

## Verification and case study

Run `npm test`, `node --test server/feedback.test.mjs`, `npm run build`, and the browser checks. Backend tests use a mock provider, not paid AI requests. No live model quality claim is made until a real provider is configured and evaluated.

The build demonstrates an AI-assisted workflow: Uthman chose evidence-linked feedback analysis; AI coding assistance implemented the interface and integration. Key decisions were to preserve the existing deterministic ratings, separate uploaded feedback from a fixed demonstration, reject unknown source IDs, clear stale analysis when data changes, and make users approve sending text. A useful failure to test is an apparently well-formed result with an invented source ID: both backend and frontend reject it. Human review still needs to assess whether cited text supports each interpretation. Evaluate real outputs with mixed opinions, sparse feedback, irrelevant content and embedded instructions before publishing live AI functionality.
